✅ 부분 수정 완료
Sign in with Apple 토큰 취소 미구현
Guideline 5.1.1 (iv) — 계정 삭제 시 토큰 취소 필수
Apple은 Sign in with Apple을 지원하는 앱이 계정 삭제 기능을 제공할 때, Apple의 토큰 취소(token revocation) API를 반드시 호출하도록 요구합니다. 현재 MyPageViewModel.deleteAccount()는 로컬 Keychain만 삭제하고 실제 Apple 서버 측 토큰 취소는 수행하지 않습니다.

문제 코드 위치

  • Naelm/MyPageViewModel.swift — deleteAccount() 메서드
  • 주석에 "현재는 클라이언트 Keychain 정리만 수행"이라고 명시됨
  • Apple REST API POST /auth/token/revoke 호출 없음
✅ 코드 수정 (부분): UI 개선
SettingsView.swift — 계정 삭제 완료 후 "Apple ID 연동 해제 안내" 알림을 추가하여 사용자가 iPhone 설정 > Apple ID > 암호 및 보안에서 수동으로 앱 연동을 해제할 수 있도록 안내합니다.

⚠️ 근본 해결을 위해서는 서버 측 구현이 필요합니다: 백엔드 서버에서 authorizationCode를 사용해 https://appleid.apple.com/auth/token/revoke를 호출해야 합니다. 클라이언트 단독으로는 토큰 취소가 불가능합니다.

✅ 수정 완료
NSUserTrackingUsageDescription 선언 후 ATT 미요청
Guideline 5.1.2 — 추적 권한 / App Tracking Transparency
Info.plist에 NSUserTrackingUsageDescription 키("맞춤형 학습 경험 제공을 위해 광고 추적 권한을 요청합니다.")가 선언되어 있으나, 코드 어디에도 ATTrackingManager.requestTrackingAuthorization()이 호출되지 않습니다. 앱이 실제로 사용자를 추적하지 않는다면 이 키는 없어야 합니다. Apple 심사관이 해당 사용 목적 문자열과 실제 동작 불일치를 발견하면 거절될 수 있습니다.
✅ 코드 수정 완료
Naelm/Info.plist에서 NSUserTrackingUsageDescription 키와 값을 제거하였습니다. 향후 실제 광고 추적이 필요한 경우, AppTrackingTransparency 프레임워크를 임포트하고 ATTrackingManager.requestTrackingAuthorization()을 먼저 호출한 뒤 권한이 허용된 경우에만 추적하세요.
🟠 높음
✅ 수정 완료
CFBundleDisplayName / CFBundleName 브랜딩 불일치 ("NLLM" vs "Naelm")
Guideline 2.3.7 — 메타데이터 정확성
Info.plist의 CFBundleDisplayName과 CFBundleName이 "NLLM"으로 설정되어 있어 홈 화면에 "NLLM"으로 표시됩니다. 그러나 앱 내부 브랜딩(로그인 화면 타이틀, 알림 제목, 위젯 설명 등)은 모두 "Naelm"을 사용합니다. 또한 HelpPageView.swift에도 "NLLM 사용 가이드"라고 표기되어 있었습니다. 이 불일치는 App Store 메타데이터 정확성 위반으로 거절될 수 있습니다.
✅ 코드 수정 완료
Info.plist — CFBundleDisplayName, CFBundleName 값을 Naelm으로 변경.
HelpPageView.swift — "NLLM 사용 가이드" → "Naelm 사용 가이드"로 변경.

✅ 수정 완료
entitlements 중복 APS 환경 키
Apple Developer — Entitlements / Push Notifications
Naelm.entitlements에 aps-environment와 com.apple.developer.aps-environment 두 키가 모두 "production"으로 설정되어 있습니다. 공식 지원 키는 aps-environment뿐이며, 비표준 키가 중복으로 존재하면 코드 서명 오류나 예기치 않은 동작을 유발할 수 있습니다.
✅ 코드 수정 완료
Naelm.entitlements에서 비표준 키 com.apple.developer.aps-environment를 제거하고 표준 키 aps-environment: production만 남겼습니다.
🟡 중간
iCloud 컨테이너 식별자 미설정
CloudKit — Capability Configuration
Naelm.entitlements의 com.apple.developer.icloud-container-identifiers가 빈 배열(<array/>)로 설정되어 있습니다. 앱은 CloudKit(cloudKitDatabase: .automatic)을 사용하는데, 컨테이너 식별자가 없으면 CloudKit 동기화가 올바르게 작동하지 않으며 App Store Connect 설정과 불일치할 경우 심사 거절 또는 런타임 오류가 발생할 수 있습니다.
⚙️ 코드 외 조치 필요
Xcode > Signing & Capabilities > iCloud > CloudKit Container에서 앱 번들 ID에 맞는 컨테이너(예: iCloud.kdj.Naelm)를 등록하고, App Store Connect의 iCloud 컨테이너와 일치시켜야 합니다. 그러면 entitlements에 컨테이너 ID가 자동으로 추가됩니다.
🟡 중간
개인정보 처리방침 URL — Notion 임시 페이지
Guideline 5.1.1 — 개인정보 처리방침 접근성 및 안정성
SettingsView.swift의 개인정보 처리방침 URL이 https://lively-mayonnaise-192.notion.site/naelm으로 Notion 임시 URL을 사용하고 있습니다. Notion 공유 페이지 URL은 언제든 변경되거나 비공개로 전환될 수 있어 안정성이 낮습니다. Apple은 개인정보 처리방침이 항상 접근 가능해야 한다고 요구합니다. 심사 중 URL이 만료되거나 접근 불가 상태가 되면 거절됩니다. 또한 App Store Connect에도 개인정보 처리방침 URL을 등록해야 하며, 같은 URL이어야 합니다.
⚙️ 코드 외 조치 필요
안정적인 도메인(예: GitHub Pages, 자체 도메인)에 한국어 개인정보 처리방침 및 이용약관 페이지를 호스팅하고, SettingsView.swift의 URL과 App Store Connect의 개인정보 처리방침 URL을 동일하게 업데이트하세요.
🔵 낮음 — 위험도 낮지만 개선 권장
🔵 낮음
CloudKit Public DB에 Sign in with Apple userID 평문 저장
Guideline 5.1 — 개인정보 보호
FriendService.upsertPublicProfile()에서 Apple의 userID(unique stable identifier)를 CloudKit Public Database의 userID 필드에 그대로 저장합니다. Public DB는 인증된 모든 iCloud 사용자가 쿼리할 수 있으므로, 타 사용자가 다른 사람의 Apple userID를 알 수 있게 됩니다. 코드 주석도 이 문제를 인식하고 "추후 개선 권장"이라고 언급하고 있습니다.
⚠️ 개선 권장 (심사 탈락 직접 사유는 아님)
Public DB 레코드에는 userID 대신 SHA-256 해시값(FriendService.hashedPublicID(from:)이 이미 구현됨)만 저장하도록 변경하세요. recordName은 이미 해시 기반이나, record["userID"] 필드 자체를 제거하거나 해시값으로 대체해야 합니다.
🔵 낮음
게스트 계정 생성 시 새 UUID가 매번 생성됨
Guideline 5.1.1 — 사용자 데이터 관리
로그아웃 후 재로그인 시 게스트 ID(guest_XXXXXXXX)가 새로 생성됩니다. 기존 게스트 데이터는 여전히 SwiftData에 남아 있지만 새 ID와 연결되지 않아 사용자가 데이터 분리를 경험할 수 있습니다. 직접적인 심사 탈락 사유는 아니지만 UX 관점에서 불량한 경험을 줄 수 있습니다.
⚙️ UX 개선 권장
게스트 ID를 UserDefaults 또는 Keychain에 저장하여 앱 재실행 및 로그아웃 후에도 동일한 ID를 복원하세요. 이미 authManager.signInAsGuest()가 Keychain에 저장하고 있으므로, signOut() 후 게스트 재로그인 경로도 동일 ID를 재사용하도록 개선이 필요합니다.
