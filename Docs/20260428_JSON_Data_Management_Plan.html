Data Management Plan

Naelm 정적 학습 데이터(JSON) 분석 및 앞으로의 관리 계획

현재 Naelm/Vocabulary.json과 Naelm/Grammar.json은 앱 최초 실행 시 SwiftData로 시딩되는 핵심 번들 데이터다. 지금처럼 단일 파일에 계속 이어붙이는 방식은 아직 동작에는 문제가 없지만, 데이터가 더 늘어날수록 검수·충돌·품질 관리 비용이 빠르게 커질 가능성이 높다.

분석 대상
Vocabulary.json / Grammar.json
현재 규모
총 1,040개 항목 / 약 837KB
핵심 결론
런타임은 유지, 관리 방식은 분리
권장 방향
소스 분할 + 빌드 산출물 통합

1. 현재 파일 상태 요약

파일 항목 수 크기 구조 특징 무결성 메모
Naelm/Vocabulary.json 520 약 308KB 단일 배열 / 모든 항목이 flat 구조 / frequencyLevel 1~4 균등 분포 중복 ID 없음 빈 필드 없음
Naelm/Grammar.json 520 약 529KB 단일 배열 / difficultyLevel 1~4 균등 분포 / blankTarget, distractors 포함 중복 ID 없음 빈 필드 없음
추가 관찰: 두 파일 모두 dataVersion은 전부 1이며, ID는 각각 vocab_001 ~ vocab_520, gram_001 ~ gram_520로 연속적이다.

2. 이 JSON 파일들이 실제로 쓰이는 곳

앱 시작 시 시딩

  • Naelm/NaelmApp.swift에서 앱 시작 시 DataLoader.seedAllIfNeeded 호출
  • Naelm/DataLoader.swift가 번들에서 두 JSON 파일을 읽고 SwiftData 모델로 변환
  • 현재 구조는 “파일명 고정 + 최상위 배열” 전제를 갖고 있음

단어 데이터 의존 지점

  • CardViewModel.swift: frequencyLevel로 학습 덱 구성
  • OnboardingView.swift: frequencyLevel, partOfSpeech, korean으로 레벨 테스트 생성
  • BookmarkListView.swift: category, partOfSpeech, frequencyLevel 필터
  • VocabularyCardView.swift: korean, synonyms, meanings 표시

문법 데이터 의존 지점

  • QuizViewModel.swift: difficultyLevel, blankTarget, distractors, quizType
  • OnboardingView.swift: 배치 테스트 문제 생성에 동일 필드 사용
  • DashboardView.swift: 오답 문법 복습 퀴즈 생성
  • MyPageViewModel.swift: category 기준 통계 집계

구조상 중요한 포인트

  • 단어는 현재 전부 flat 구조지만, 로더는 이미 meanings 배열도 수용 가능
  • 문법은 오답 보기 품질이 JSON 품질과 직접 연결됨
  • 즉, 단순 저장소가 아니라 “학습 로직 입력값” 역할까지 수행 중

3. 지금 방식이 앞으로 비효율적일 수 있는 이유

편집 충돌 증가 운영 리스크

한 파일 끝에 계속 추가하면 작업자가 많아질수록 Git 충돌이 늘고, 리뷰 시 실제 변경 범위를 파악하기도 어려워진다.

검수 단위가 너무 큼 품질 리스크

단어 10개만 추가해도 수백 개가 들어 있는 거대한 파일 diff를 검토하게 되어 오탈자, 중복, 레벨 오분류를 놓치기 쉽다.

구조 변경이 어려움 확장 리스크

예를 들어 multi-meaning 단어, 예문 보강, 태그 추가 같은 변경이 생기면 전체 파일을 한 번에 손봐야 해서 부담이 커진다.

런타임과 원본 관리가 섞여 있음 설계 이슈

현재 JSON은 “앱이 읽는 최종 산출물”이면서 동시에 “사람이 직접 관리하는 원본” 역할도 같이 하고 있다.

4. 권장 방향: 원본은 쪼개고, 앱에는 합쳐서 넣기

가장 안전한 방향은 앱 런타임이 읽는 번들 구조는 당장 유지하면서, 사람이 관리하는 원본만 작은 파일들로 분리하는 것이다.

왜 이 방향이 좋은가

  • 현재 앱 로직을 거의 안 건드려도 됨
  • 기존 DataLoader와 시딩 흐름을 그대로 유지 가능
  • 데이터 관리만 먼저 개선할 수 있음
  • 필요하면 나중에 다중 파일 로딩으로 확장 가능

핵심 개념

  • Source of Truth: 잘게 나뉜 원본 JSON 파일들
  • Build Artifact: 앱 번들에 포함될 최종 Vocabulary.json, Grammar.json
  • Validation: 병합 전 ID·필수 필드·분포 체크

5. 추천 관리 구조

데이터 추천 원본 분리 기준 이유 최종 번들 형태
Vocabulary frequencyLevel 기준 1차 분리, 필요 시 카테고리 기준 2차 분리 현재 학습 로직이 레벨 중심으로 동작하고, 리뷰/추가 작업도 레벨 단위로 나누기 쉬움 빌드 시 하나의 Vocabulary.json으로 병합
Grammar difficultyLevel + category 또는 quizType 기준 분리 문법은 문제 성격별 검수 포인트가 달라서 카테고리/유형별 관리가 유리함 빌드 시 하나의 Grammar.json으로 병합
예시 디렉터리 개념: DataSources/Vocabulary/level-1/*.json, DataSources/Grammar/level-2/preposition/*.json

6. 앞으로의 실행 계획

1

원본 관리용 디렉터리 분리

  • 기존 거대 JSON을 직접 편집하지 않고, 작은 원본 파일 집합으로 관리 체계를 전환
  • 단어/문법 각각에 대해 분리 기준과 파일명 규칙을 먼저 고정
2

병합 규칙과 스키마 규칙 정의

  • ID 규칙, 필수 필드, 허용 레벨값, 카테고리 표기 규칙을 문서화
  • distractors 개수/구분자, blankTarget 실제 포함 여부 같은 품질 규칙도 명시
3

자동 병합 + 검증 단계 도입

  • 작은 원본 파일들을 하나의 최종 JSON으로 자동 병합
  • 병합 전에 중복 ID, 누락 필드, 분포 이상, 예문-정답 불일치를 검사
  • 문제 없을 때만 번들용 JSON 산출
4

앱 런타임 구조는 당분간 유지

  • DataLoader는 계속 최종 Vocabulary.json, Grammar.json만 읽게 유지
  • 즉, 관리 개선과 앱 동작 변경을 분리해서 리스크를 낮춤
5

데이터 규모가 더 커질 때 2차 고도화 검토

  • 파일 수와 항목 수가 더 커지면 다중 번들 파일 로딩 또는 서버/콘텐츠 관리 방식 검토
  • 하지만 지금 단계에서는 먼저 “원본 분리 + 산출물 통합”만 해도 충분히 효과가 큼

7. 우선순위 제안

지금 바로 할 것 추천

  • 원본 데이터 분리 기준 확정
  • 작은 파일 단위 관리 시작
  • 최종 번들 JSON 자동 생성 체계 준비

나중에 검토할 것

  • DataLoader의 다중 파일 직접 로딩
  • 원격 업데이트 또는 CMS 연동
  • 데이터 수정 이력/승인 워크플로우 도입

8. 최종 판단

현재 두 JSON 파일의 크기 자체가 당장 앱 성능 문제를 만들 정도는 아니다. 다만 앞으로 계속 같은 방식으로 누적 편집하는 것은 운영 효율 면에서 불리하다. 따라서 가장 현실적인 다음 단계는 데이터 원본을 작은 파일로 분리해 관리하고, 앱에는 기존처럼 단일 최종 JSON만 공급하는 구조로 바꾸는 것이다.

이 방식이면 현재 코드 의존성을 깨지 않으면서도 데이터 추가, 검수, 협업, 확장성 문제를 동시에 완화할 수 있다.
